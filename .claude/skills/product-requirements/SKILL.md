# 需求澄清

把模糊需求变成清晰可交付的 issue 内容。通过质量评分迭代，确保需求达到 90 分后再写入 issue。

## 核心理念

- **角色**：严谨的 Product Owner
- **方法**：100 分质量评分，90 分阈值
- **输出**：issue body 内容（不是本地文件）

## 工作流

### Step 1：理解上下文

1. 读取项目 README、package.json 了解技术栈
2. 如果是 Coding Teams 项目，参考 `docs/architecture.md` 和 `docs/api/coding-teams.md`
3. 结合项目上下文理解用户需求
4. 确认理解是否正确

### Step 2：质量评分（100 分制）

| 维度 | 分值 | 关注点 |
|------|------|--------|
| 业务价值与目标 | 30 | 问题陈述、成功指标、预期成果 |
| 功能需求 | 25 | 用户故事、验收标准、边界处理 |
| 用户体验 | 20 | 用户画像、交互流程、UI 偏好 |
| 技术约束 | 15 | 性能、安全、集成 |
| 范围与优先级 | 10 | MVP 定义、交付阶段 |

展示格式：
```
📊 需求质量评分：[总分]/100

- 业务价值与目标：[X]/30
- 功能需求：[X]/25
- 用户体验：[X]/20
- 技术约束：[X]/15
- 范围与优先级：[X]/10

[< 90]：需要进一步澄清...
[≥ 90]：质量达标，可以生成 issue。
```

### Step 3：针对性提问

分数 < 90 时，优先补齐最低分维度。**每轮只问 2-3 个问题**。

各维度典型问题：

**业务价值（< 24/30）**：
- 要解决什么具体问题？
- 如何衡量成功？
- 不做会怎样？

**功能需求（< 20/25）**：
- 主要用户流程是什么？
- 边界情况如何处理？
- 必须有 vs 最好有的功能？

**用户体验（< 16/20）**：
- 主要用户是谁？
- 理想体验是什么样的？

**技术约束（< 12/15）**：
- 性能期望？
- 安全/合规要求？
- 需要和什么系统集成？

**范围（< 8/10）**：
- MVP 最小范围？
- 优先级排序？

### Step 4：迭代

每次用户回答后：
1. 更新理解
2. 重新评分
3. 展示进步："这个回答把 [维度] 从 X 提升到了 Y"
4. 直到 90+

### Step 5：输出

达到 90 分后，输出结构化的 issue body 内容，包含：

1. **背景**：问题与影响
2. **目标/方案**：高层方案
3. **验收标准**：checkbox 列表
4. **测试用例**：TC-ID + 描述 + 详细步骤
5. **技术说明**：风险、依赖、参考文档
6. **验证方式**：测试命令

这些内容可以直接用 `/create-issue` 创建为 GitHub issue。

## 质量检查清单

- [ ] 有清晰的问题陈述
- [ ] 验收标准可测试
- [ ] 测试用例覆盖所有验收标准
- [ ] 边界和错误场景已考虑
- [ ] 技术风险已识别
- [ ] 范围边界明确（In/Out of scope）
